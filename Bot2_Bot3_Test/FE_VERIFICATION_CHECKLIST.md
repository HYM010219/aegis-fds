# FE 확인 순서: 순환거래와 고빈도 송금 두 개

## 이번 테스트가 확인하는 것

**보고서의 숫자가 Spark의 어떤 계산 결과에서 나왔는지 찾을 수 있고, 사건 상세·STR 팝업·다운로드 TXT가 같은 결과를 쓰는지 확인한다.** 단순히 사건이 생성되거나 화면이 열리는 것만으로 통과하지 않는다.

대상은 **L8 순환거래와 R01 고빈도 송금, 두 개**다. R04는 별도의 추가 시험 기록이며 이번 두 규칙 확인 대상에 넣지 않는다. 별도 Spark 집계 화면·새 버튼을 만들지 않고 기존 화면에서 확인한다. FE 담당자의 기존 코드와 DE 담당자의 Spark 코드를 덮어쓰지 않는다.

## 시작 전에: 사건 번호만으로는 어디서든 조회되지 않는다

아래 성공한 사건은 **BE의 로컬 DB에 저장된 사례**다. FE가 다른 서버나 다른 DB를 보고 있으면 그 번호로는 조회되지 않는다. GitHub에서 이 폴더를 받는다고 사건 데이터가 복사되지는 않는다.

진행 방식은 다음과 같다.

1. **BE가** FE 화면이 연결할 테스트 서버를 준비하고 접속·인증 방법을 전달한다.
2. **BE가** 그 서버에서 테스트 데이터를 넣는다. FE는 주입 스크립트를 실행하지 않는다.
3. **BE가** 거기서 나온 사건 번호를 FE에게 전달한다. 다른 DB에서 새로 실행하면 아래 번호와 다른 번호가 나오는 것이 정상이다.
4. **FE가** 그 번호로 기존 사건 상세와 STR을 열어 아래 표를 비교한다.

전달 문구:

> 제가 테스트 데이터를 넣고 사건 번호를 드릴게요. 그 번호로 기존 사건 상세와 STR 초안을 열어서 숫자와 근거가 같은지 확인해 주세요. 지금 아래 번호는 로컬 검증 기록이라, 연결한 서버가 다르면 그대로 조회되지 않을 수 있습니다.

BE가 채워서 전달할 정보:

| 항목 | 전달할 값 / 현재 상태 |
|---|---|
| FE가 접속할 화면·API 주소 | BE가 준비 후 기입. 현재 이 문서에 확정 주소 없음 |
| 화면이 보는 DB에 두 사건이 있는가 | BE 확인 필요. 아래 번호는 로컬 사례 |
| L8 사건 번호 | 아래 성공 번호 또는 새로 주입한 서버에서 나온 번호 |
| R01 사건 번호 | 아래 성공 번호 또는 새 서버 번호. 기존 화면 노출 상태도 함께 확인 |
| 인증·프록시 설정 | BE가 FE에게 별도 전달. 실제 키는 Git에 넣지 않음 |

AWS 침지테스트 환경과 로컬 시험 결과를 구분한다. 이 자료가 AWS에 같은 코드·데이터가 있다는 뜻은 아니다. 현재 침지테스트에 데이터를 추가로 주입하는 작업은 이 문서 확인에 포함되지 않는다.

## 두 성공 사례와 현재 확인 범위

| 규칙 | 성공한 사건 번호 | 기대값 | 현재 상태 |
|---|---|---|---|
| L8 순환거래 | `6b05018f0591fcf002525477` | A→B→C→A, 10,000→9,500→9,000 USDT, 회수율 90% / 기준 80% | 로컬 그래프·서버 STR 검증 스크립트 성공. 최신 FE 화면·TXT 확인은 아래 순서로 진행 |
| R01 고빈도 송금 | `3039ff84943095ae77742489` | 최근 5분 요청 6건 / 기준 5건, 금액 720 USDT, 상대 주소 1곳 | 로컬 기존 사건·STR API 대조 성공. 기본 경보 목록에서는 숨김. 기존 FE에서 바로 확인 가능한 완료 상태는 아님 |

**R01이 목록에 없으면 FE 오류로 판정하지 않는다.** BE 검증용 관측 사건을 기본 목록에서 숨긴 현재 계약 때문이다. BE는 검증 서버에서 R01을 기존 사건으로 노출하는 방식과 응답 호환성을 담당자와 정리한 후 FE에게 확인을 요청해야 한다. FE에게 새 화면을 만들거나 해당 제한을 우회하라고 요청하지 않는다. 이 문서 추가로 노출 방식이 변경되지는 않았다.

## FE가 실제로 확인하는 순서

1. BE가 알려준 서버·사건 번호를 사용한다. 경보 목록에서 사건을 열거나 기존 사건 URL `/admin/#/cases/{case_id}`로 들어간다. R01은 BE가 기존 화면 조회 가능하다고 확인한 뒤 진행한다.
2. 사건 상세의 규칙·판정 근거·관련 거래를 확인한다. L8은 기존 자금 흐름 그래프도 확인한다.
3. 기존 **STR 초안** 버튼을 누른다.
4. 아래 비교표를 확인한다. 출처가 화면에 표시되지 않으면 개발자 도구 Network에서 기존 사건 상세·STR API 응답을 확인한다. 이를 위해 새 화면이나 필드를 임의로 추가하지 않는다.
5. 기존 **내려받기 (.txt)**로 받은 파일과 팝업의 숫자·근거를 비교한다.
6. 감사로그에서 해당 사건의 STR_DRAFT 기록을 확인한다. 실패하면 실패 위치·API 상태코드를 기록한다.
7. 문서 마지막 결과표에 PASS/FAIL/확인 불가를 남긴다.

## 무엇과 무엇이 같아야 하는가

| 비교 항목 | 어디를 비교하는가 | 통과 기준 |
|---|---|---|
| 사건·대상·규칙 | 사건 상세 ↔ STR 응답·본문 ↔ TXT | 같은 사건 ID, 지갑 주소, 규칙 |
| 근거 버전 | 상세 응답의 스냅샷 ID ↔ STR 응답·본문 | 같은 ID. 숫자가 우연히 같기만 한 것은 불충분 |
| 실측값·기준값 | 상세 판정 근거 ↔ STR 팝업 ↔ TXT | 숫자와 단위가 같음. L8 90%/80%, R01 6건/5건 |
| 금액 | 상세 근거 ↔ STR 팝업 ↔ TXT | 같은 금액 정의와 값. 승인 금액과 요청 시도 금액을 섞지 않음 |
| 집계 구간 | 상세 API 근거 시작·종료 ↔ STR | 같은 시간 구간. UTC와 한국 시간은 9시간 차이를 환산해 비교 |
| 계산 출처 | 상세 근거의 엔진·쿼리·배치 ↔ STR 출처 | 어떤 Spark 계산 결과인지 같은 값으로 추적 가능 |
| 원본 입력 | 상세 근거의 event_id/tx_hash/request_id ↔ STR 근거 이벤트 | 같은 원본 이벤트를 참조 |
| 최종 파일 | STR 팝업 ↔ 다운로드 TXT | 같은 근거와 수치. 다운로드 시 다른 값으로 재계산하지 않음 |

로컬 검증 응답은 `evidence_snapshot.source`, `snapshot.source`를 사용한다. 최신 integration FE는 `report.provenance`의 `computed_by`, `spark_batch_id` 등도 사용한다. BE가 실제 연결 서버의 응답 형식을 확인해서 전달한다. 서로 다른 버전의 필드 이름만 비교해 실패 처리하거나 로컬 응답 모양으로 최신 코드를 덮어쓰지 않는다. 동일한 계산 근거 식별자가 전달되지 않는다면 “출처 연결 확인 불가”로 기록한다.

## L8: 그대로 대조할 값

```text
run_id: verify-f40584f2-3cc1-4766-ad88-a715f7168e89
case_id: 6b05018f0591fcf002525477
snapshot_id: 04590f755fe1f5aa6b8a26166221c85fbbe784b057425e666a4b6ad39cf721ba
계산 엔진: spark_mongo_detector
Spark batch: 18788
순환 경로: A → B → C → A
금액 USDT: 10,000 → 9,500 → 9,000
회수율: 9,000 / 10,000 = 90%
회수율 기준: 80%
그래프: 노드 7, 간선 7, 탐지 경로 3
```

7건이 모두 승인된 뒤 Spark가 순환을 탐지한 사례다. 입구에서 7건을 차단한 사례가 아니다. L8 계산 출처는 Kafka를 계기로 Mongo 거래를 조회하는 기존 Spark 탐지기이며, Delta 요청 집계와 같은 경로라고 설명하지 않는다.

## R01: 그대로 대조할 값

```text
run_id: verify-c91ebb56-62ed-484d-9428-c6402d2ef159
case_id: 3039ff84943095ae77742489
snapshot_id: 1cc894e7e5fe8a4b21b343987a736311709a9a768deede2020169fff19c7232a
계산 엔진: spark_structured_streaming
Spark query: requests-v2-5m
Spark batch: 18
최근 5분 요청 횟수: 6건 / 기준 5건
요청 금액 합계: 720.000000 USDT
서로 다른 수신 주소: 1곳
Gateway: 승인 5건, 거절 1건 (5번째 승인 후 보류)
```

Spark의 6건·720 USDT는 **판정 전 요청 시도** 집계이므로 마지막 거절 요청도 포함한다. 승인 5건의 금액과 같아야 한다고 비교하지 않는다. 사건의 최초 탐지 스냅샷을 고정하며, 최신 집계가 증가해도 과거 보고서의 숫자를 바꾸지 않는다.

주소별 1분 건수·금액은 `requests-v2-1m`, 최근 5분 횟수·상대 수는 `requests-v2-5m`에서 계산한다. 모든 요청이 같은 1분에 들어온 경우에만 해당 1분이 6건·720 USDT다. 분 경계를 넘었으면 원본 시각으로 각 1분을 나눠 비교한다. 여러 5분 Sliding 구간의 건수를 합산하지 않는다. 이 집계 검증은 BE/DE가 수행해 근거를 전달하며 FE에 별도 집계 화면을 요구하지 않는다.
